# 怎么搭这棵树

脑图要回答的是「用户怎么用它」，不是功能清单。动笔前先读完要覆盖的全部资料（原型源码、产品说明、App 源码页面文案、调研报告），再定结构。

## 两种常见骨架

**A. 自家产品（原型 + 应用）**

```
产品
├─ 设备端（当前版本）
│   ├─ 硬件与输入            每个输入件一条
│   ├─ 首页 / 主界面          操作 → 反应，逐条
│   ├─ 各面板 / 页面          每个都写：怎么打开、怎么关、按键在这里代表什么、长按菜单有什么
│   ├─ 应用内规则
│   ├─ 语音 / AI 链路
│   └─ 手势与按键规则速查    阈值写真实数值
├─ 手机 App                  按一级页分支，叶子取自源码里的真实文案
├─ 跨端功能（如来电代接）    设备侧 + 手机侧放在一支里
├─ 设备上的应用
└─ 旧版原型（如有）          单独一支，标「原型」，不和新版混写
```

同一个键在不同上下文含义不同，必须分别写在各自的面板下，不能压成一张总表。两代交互模型并存时，各自成支，页面底部用 `meta.extraHtml` 放一张「两代交互对照」表。

**B. 竞品调研**

```
品类全景
├─ 分类 1（如 带屏·贴手机）
│   └─ 产品 X
│       ├─ 按钮交互           每个按键操作一条：长按 / 双击 / 灯色 / 震动
│       └─ 软件交互           屏幕显示什么、App / AI 做什么
├─ 分类 2 …
└─ 收口（如 屏幕角色三级进化）
```

只保留「软件交互 + 硬件按钮交互」两个维度，单侧展开，不写硬件参数。每个产品的叶子尽量对应一张真实的功能场景截图。

## 状态徽标

徽标表达「这条结论有多可靠」，团队一眼就能分辨哪些已在实物上验证：

| 码 | 默认文字 | 用在 |
|---|---|---|
| `ok` | 实机 | 在真实设备 / 已上市产品上见过 |
| `pv` | 预览 | 只在电脑预览、仿真里跑过 |
| `cs` | 特定版本 | 只在某个固件版本 / 地区版本里有（文字在 legend 里改） |
| `br` | 开发中 | 在开发分支，未合并或未发货 |
| `td` | 待做 | 已知缺口 |
| `sm` | 原型 | 网页模拟、概念稿 |

只在节点真有区别时加，不要每个节点都挂。

## 写法

- 节点标题写动作和结果：「长按 600 ms → 说话」比「语音功能」有用。
- `d` 只写一行补充，数值照抄资料（48 px、1/3 行程、600 px/s）。
- 资料里没有的不要写。推测出来的结论不放进脑图，放进对话里说明。
- 一级分支一般 3–6 支，每支下 4–9 个二级节点；更深的放到三、四级，首屏只展开到二级。
